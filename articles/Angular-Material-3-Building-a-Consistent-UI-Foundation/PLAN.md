# Статья №9 — Angular Material 3: создание единой основы пользовательского интерфейса

**Статус:** запланирована. Рабочее название и номер статьи утверждены. План подготовлен; реализация и написание статьи ещё не начаты.

## Цель статьи

Превратить интерфейс приложения Personal Finance в целостный и удобный пользовательский интерфейс, используя Angular Material и Material 3 в качестве основы.

Основное внимание уделяется практической реализации интерфейса, а не отдельной методологии UX-дизайна или созданию собственной библиотеки компонентов с нуля.

## Планируемые темы

1. **Angular Material как основа пользовательского интерфейса.** Выбор и применение компонентов Angular Material в приложении.

2. **Темизация Material 3.** Настройка тем, цветовых схем, типографики и состояний компонентов.

3. **Design Tokens.** Централизованное управление цветами, типографикой, размерами, отступами, радиусами скругления и другими визуальными параметрами.

4. **Интеграция с SCSS.** Организация стилей и согласование пользовательских стилей с Angular Material и системой дизайн-токенов.

5. **Повторно используемые UI-компоненты.** Создание общих компонентов поверх Angular Material только там, где повторное использование действительно оправдано.

6. **Dashboard.** Представление финансового баланса, доходов, расходов и ключевых показателей.

7. **Интерфейс управления транзакциями.** Разработка списка транзакций, форм, фильтров, категорий и действий над транзакциями.

8. **Единый пользовательский интерфейс приложения.** Приведение экранов, диалоговых окон, меню, таблиц и форм к единой визуальной системе.

## Практическая часть

### Интернационализация приложения (i18n)

Для интернационализации приложения использовать `@ngx-translate/core` версии 18.

Поддерживаемые языки:

- Английский (`en`) — язык интерфейса по умолчанию.
- Немецкий (`de`).
- Русский (`ru`).

Требования:

- Все пользовательские тексты приложения должны поступать исключительно из системы i18n.
- Переключение языка должно поддерживаться во время работы приложения без перезагрузки.
- Переводы хранятся в отдельных JSON-файлах для каждого языка.
- Для каждого языка используется одинаковая структура ключей.
- Все три языковых JSON-файла должны обновляться одновременно.
- Русская версия (`ru.json`) является ведущей и определяет исходное содержание переводов.
- Английская и немецкая версии должны соответствовать актуальной русской версии.
- Добавление, изменение или удаление переводов выполняется одновременно во всех трёх файлах.
- При первом запуске приложения используется английский язык (`en`).
- Выбранный пользователем язык сохраняется и восстанавливается при повторном запуске приложения.

**Переключатель языка в Page Header:**

Переключатель языка располагается в Page Header непосредственно слева от переключателя темы.

Для выбора языка используется стандартное меню Angular Material (`MatMenu`). Использование `MatSelect` для этой задачи не предусматривается.

Закрытое состояние переключателя:

- Отображается флаг текущего языка и его двухбуквенный код.
- Код языка всегда отображается заглавными буквами: `EN`, `DE`, `RU`.
- Флаг располагается слева от кода.

Выпадающее меню:

- Содержит три пункта в фиксированном порядке: `EN`, `DE`, `RU`.
- Каждый пункт содержит флаг слева и двухбуквенный код языка заглавными буквами.
- Текущий выбранный язык остаётся видимым в меню, но соответствующий пункт имеет состояние `disabled`.
- Остальные языки доступны для выбора.
- При выборе другого языка интерфейс переключается без перезагрузки приложения.

**Поведение при скрытии Page Header:**

- Переключатель языка скрывается вместе с Page Header.
- При возвращении Page Header переключатель языка снова отображается.
- Переключатель языка не перемещается в Toolbar и не дублируется в других частях интерфейса.

**Архитектура:**

- В библиотеке `libs/shared/base` создать сервис для упрощения доступа к переводам.
- Сервис инкапсулирует взаимодействие с механизмом интернационализации.
- Компоненты и другие части приложения используют согласованный механизм получения переводов.
- Универсальные UI-компоненты не должны содержать собственных пользовательских текстов.

### 1. Управление темой приложения

Добавить переключатель темы на страницах Login и Dashboard.

Предусмотреть три режима:

- **Light:** принудительное использование светлой темы.
- **Dark:** принудительное использование тёмной темы.
- **System:** автоматическое определение темы на основании системных настроек операционной системы.

**Поведение переключателя:**

- Переключатель реализуется в виде одной кнопки, без выпадающего списка.
- Каждое нажатие циклически переключает режим темы в следующем порядке:

  `Light → Dark → System → Light`

- Иконка кнопки должна соответствовать текущему выбранному режиму:
  - Light — солнце;
  - Dark — луна;
  - System — компьютер.
- Иконка всегда отражает выбранный режим, а не фактически отображаемую тему.

**Требования к реализации:**

- Переключение темы должно работать на обеих страницах.
- Выбранный режим должен корректно определять используемую тему приложения.
- В режиме System приложение должно учитывать изменения системной темы.
- На Dashboard выбранное пользователем состояние переключателя должно сохраняться в LocalStorage.
- Сохранение и получение настройки должны выполняться через существующую архитектуру Facade и DAL, без прямого обращения компонентов к LocalStorage.
- При повторном открытии приложения должна восстанавливаться сохранённая настройка.

**Реализация переходов между состояниями:**

Для описания последовательности переключения использовать типизированную таблицу переходов `Record<Theme, Theme>`.

Обновление состояния выполнять через Angular Signal:

```ts
type Theme = 'light' | 'dark' | 'system';

const next: Record<Theme, Theme> = {
  light: 'dark',
  dark: 'system',
  system: 'light'
};

this.theme.update(current => next[current]);
```

Такой подход обеспечивает типобезопасность переходов и исключает необходимость реализовывать последовательность переключения через условные конструкции.

### 2. Таблица транзакций Dashboard — фильтрация и Toolbar

Над таблицей транзакций создать единый Toolbar для управления отображаемыми данными.

Toolbar должен объединять управление типом транзакций и выбор временного периода.

**Управление типом транзакций:**

Предусмотреть две кнопки с иконками:

- Income — приходные транзакции;
- Expense — расходные транзакции.

Кнопки должны визуально показывать активное состояние выбранного фильтра. При взаимодействии с ними таблица должна отображать соответствующий набор транзакций.

**Фильтр по временному периоду:**

В Toolbar добавить выпадающий список со следующими вариантами:

- текущий календарный месяц — значение по умолчанию;
- последние 30 календарных дней;
- последние 60 календарных дней;
- последние 90 календарных дней;
- последние 180 календарных дней;
- пользовательский период (Custom);
- год / месяц.

**Пользовательский период (Custom):**

При выборе Custom в Toolbar дополнительно отображаются два поля:

- Date From — дата начала периода;
- Date To — дата окончания периода.

Требования к выбору дат:

- ручной ввод даты с клавиатуры запрещён;
- поля предназначены исключительно для отображения выбранных дат;
- при нажатии на поле должен открываться календарный контейнер (Angular Material Datepicker);
- пользователь выбирает дату непосредственно в календаре;
- после выбора дата отображается в соответствующем поле;
- выбор дат должен позволять задать начало и конец пользовательского периода.

**Фильтр «Год / месяц»:**

При выборе этого варианта вместо полей Date From и Date To отображаются два поля:

- Year — выбор года;
- Month — выбор месяца.

Требования:

- доступный диапазон лет определяется минимальной и максимальной датами транзакций в БД;
- список доступных месяцев зависит от выбранного года и фактического диапазона дат в БД;
- нельзя выбрать период, для которого отсутствуют соответствующие даты в БД;
- выбранные год и месяц определяют календарный месяц фильтрации таблицы;
- фильтр применяется совместно с фильтром типа транзакций и остальными фильтрами.

Фильтрация по периоду и типу транзакций должна применяться к таблице одновременно.

**Фильтр по наличию заметки:**

Добавить в Toolbar фильтр «Транзакции с заметками». При его включении таблица должна показывать только транзакции, для которых существует заметка. Фильтр применяется совместно с фильтрами по типу и временному периоду.

**Настройки таблицы:**

В Toolbar добавить кнопку «Настройки».

При нажатии открывается диалог настроек таблицы транзакций с двумя вкладками:

- Expense — настройки расходных транзакций;
- Income — настройки приходных транзакций.

Обе вкладки используют один и тот же переиспользуемый компонент настроек.

Компонент содержит два параметра:

1. Максимальная сумма отдельной транзакции для визуального выделения (иллюминации).
2. Месячный порог суммы.

Для Expense месячный параметр задаёт максимальную сумму расходов.
Для Income месячный параметр задаёт минимальную сумму доходов.

Всего предусмотрено четыре независимых значения:

- Expense transaction highlight threshold;
- Expense monthly threshold;
- Income transaction highlight threshold;
- Income monthly threshold.

Все четыре значения сохраняются в LocalStorage в виде JSON-строки как единый объект. Каждое поле объекта может иметь значение `undefined`, если соответствующая настройка не задана.

**Контроль месячных лимитов:**

Месячные суммы рассчитываются исключительно в пределах одного календарного месяца.

Для расходов:

- если сумма расходов за выбранный месяц превышает установленный Expense monthly threshold, показывается красный alert;
- текст: «вы установили максимальную сумму расходов в месяц и превысили её».

Для доходов:

- если сумма доходов за выбранный месяц меньше установленного Income monthly threshold, показывается красный alert;
- текст: «сумма ваших доходов в месяц не достигла установленной».

Алерты:

- показываются при открытии Dashboard;
- рассчитываются для выбранного в фильтре календарного месяца;
- используют все транзакции выбранного месяца, независимо от поиска и фильтра наличия заметки;
- не рассчитываются по суммам за несколько месяцев или произвольный период.

### Экспорт данных

Добавить в Toolbar кнопку «Экспорт».

**Расположение кнопки:**
- Кнопка располагается в правой части Toolbar.
- Если переключатель темы находится в Toolbar, кнопка экспорта располагается непосредственно перед ним.
- Если переключатель темы находится в Page Header, кнопка экспорта остаётся в правой части Toolbar.
- Кнопка должна быть доступна независимо от положения Page Header.

**Контекстное меню экспорта:**

При нажатии на кнопку открывается контекстное меню с выбором формата:
- Экспорт в Excel.
- Экспорт в CSV.

Если среди отображаемых строк есть выделенные строки, меню дополнительно содержит пункт «Экспорт выделенных строк» с вложенным меню:
- Экспорт в Excel.
- Экспорт в CSV.

Вложенное меню открывается при наведении курсора мыши на пункт «Экспорт выделенных строк».

**Область экспортируемых данных:**

Обычный экспорт должен включать только транзакции, отображаемые в таблице на момент запуска экспорта. Экспортируемый набор всегда является результатом действующей фильтрации и поиска. Экспорт не должен самостоятельно получать полный набор транзакций из DAL или обходить действующие ограничения отображения.

При выборе «Экспорт выделенных строк» экспортируются только выделенные транзакции из текущего отображаемого набора. Строки, скрытые действующими фильтрами или поиском, в экспорт не включаются.

**Структура экспортируемых данных:**

Экспортируемые данные могут содержать дополнительные столбцы для маркировки строк и комментариев.

Правила формирования столбцов:

1. **Столбец маркировки:**
   - Если среди экспортируемых транзакций есть хотя бы одна маркированная строка, в начале таблицы создаётся дополнительный столбец.
   - Для маркированных строк в нём указывается символ `x`.
   - Для остальных строк ячейка остаётся пустой.
   - Если маркированных строк нет, столбец не создаётся.

2. **Столбец комментариев:**
   - Если хотя бы одна экспортируемая транзакция имеет заметку, создаётся дополнительный столбец «Комментарии».
   - В нём размещается текст заметки соответствующей транзакции.
   - Для транзакций без заметки ячейка остаётся пустой.
   - Если среди экспортируемых транзакций нет ни одной заметки, столбец не создаётся.

Оба дополнительных столбца формируются независимо друг от друга.

**Имя экспортируемого файла:**

- Имя файла формируется вне библиотеки `shared/export`.
- Формирование имени выполняется на уровне соответствующего Facade, отвечающего за данные таблицы транзакций.
- Facade формирует имя с учётом действующих условий фильтрации и режима экспорта.
- Готовое имя файла передаётся в библиотеку `export` как входной параметр.
- Библиотека `export` не анализирует фильтры, не знает о транзакциях и не генерирует имена файлов самостоятельно.
- Библиотека использует переданное имя и добавляет расширение в соответствии с выбранным форматом (`.xlsx` или `.csv`).

**Архитектура системы экспорта:**

Реализацию экспорта вынести в отдельную библиотеку NX:

`libs/shared/export`

Библиотека является самостоятельным модулем общего назначения и не должна зависеть от конкретной предметной области или модели транзакций.

Требования:
- Библиотека принимает подготовленные данные извне.
- Формирование набора данных для экспорта остаётся ответственностью вызывающей стороны.
- Библиотека принимает готовое имя файла извне; генерация имени не входит в её ответственность.
- Библиотека предоставляет механизмы экспорта в поддерживаемые форматы.
- Первоначально поддерживаются Excel и CSV.
- Архитектура должна допускать последующее использование библиотеки для экспорта других сущностей приложения без привязки к транзакциям.

**NX tags:**
- `level:shared`
- `tag:export`

**Правила зависимостей:**
- UI-компоненты могут импортировать библиотеку `export`.
- Библиотека `export` может импортировать `facades`, `dal` и `base`.
- Библиотеки `facades`, `dal` и `base` не должны зависеть от `export`.
- Другие библиотеки не должны импортировать `export`, кроме UI-компонентов.

### Универсальный компонент Toolbar

Реализовать универсальный переиспользуемый компонент Toolbar в существующей библиотеке `libs/shared/ui`.

Toolbar не должен содержать бизнес-логику конкретных страниц или предметных областей. Его состав и поведение определяются конфигурацией, переданной извне.

#### 1. Структура Toolbar

Toolbar состоит из списка секций (`Sections`).

Каждая секция является отдельным переиспользуемым компонентом и содержит список элементов (`Items`).

#### 2. Section Component

Компонент Section отвечает за размещение и оформление элементов своей секции.

Параметры секции:

- `items` — список элементов секции;
- `class` — CSS-класс для индивидуального оформления секции;
- `textAlign` — выравнивание текста: `left`, `right` или `center`.

Для допустимых значений `textAlign` необходимо определить константу и генерировать TypeScript-тип на её основании. Это должно обеспечивать IntelliSense и подсказки IDE при конфигурировании секций.

#### 3. Section Item — общая модель

Все элементы секции должны иметь общий контракт:

- `id` — обязательный уникальный идентификатор элемента;
- `type` — тип элемента, определяющий его конкретную конфигурацию;
- `callback` — callback-функция, определяющая действие при взаимодействии с элементом.

Остальные параметры зависят от конкретного типа элемента и описываются отдельными интерфейсами.

Допустимые типы элементов определяются через константу с генерацией TypeScript-типа из её значений. Это обеспечивает подсказки IDE и выбор допустимых типов при конфигурировании.

#### 4. Поддерживаемые типы Section Item

На первом этапе предусмотреть следующие типы:

**Button**

Кнопка на основе Angular Material 3.

Параметры:

- `style` — вариант оформления кнопки Angular Material 3;
- `text` — необязательный текст;
- `icon` — необязательная иконка;
- `callback` — действие при нажатии.

Кнопка может отображаться:
- только с текстом;
- только с иконкой;
- одновременно с текстом и иконкой.

Конфигурация без текста и иконки недопустима. Разработчик должен получить немедленное сообщение об ошибке. Проверку необходимо по возможности обеспечить средствами TypeScript на этапе разработки.

**Dropdown**

Выпадающий список.

Параметры элемента определяются отдельным интерфейсом. Выбранное значение передаётся через `callback`.

**Date Range**

Элемент выбора пользовательского периода.

Предусматривает выбор двух дат:
- Date From;

Выбор выполняется с использованием календарных компонентов Angular Material.

**Year / Month**

Элемент выбора календарного года и месяца.

Параметры и допустимые значения определяются отдельным интерфейсом.

**Text**

Информационный текстовый элемент.

Параметры:
- текст для отображения.

Поведение:

- обрезание оформляется градиентом с переходом к 100% прозрачности;
- при наведении мыши отображается Tooltip с полным текстом.

#### 5. Отдельные компоненты для Section Item

Для каждого типа Section Item создать отдельный custom dummy component.

Предусмотреть компоненты:

- Button Item Component;
- Dropdown Item Component;
- Date Range Item Component;
- Year / Month Item Component;
- Text Item Component.

Каждый компонент:

- имеет ровно один `input`;
- использует Angular Signal Input;
- получает объект параметров, описанный соответствующим интерфейсом;
- самостоятельно отвечает за визуальное представление своего типа элемента;
- вызывает переданный `callback` при соответствующем взаимодействии.

Стандартные элементы управления Angular Material не должны передаваться в Section непосредственно. Section работает только с типизированными объектами Section Item, а их визуальное представление делегируется соответствующим custom components.

#### 6. Использование в Dashboard

Существующий Toolbar Dashboard перевести на новую универсальную реализацию.

Фильтры, выбор периода, настройки таблицы, маркировка строк, экспорт и переключатель темы должны конфигурироваться через Sections и соответствующие Section Items.

Положение и группировка элементов определяются конфигурацией вызывающей стороны, а не внутренней логикой универсальных компонентов.

Универсальные Toolbar и Section не должны знать о транзакциях, фильтрах, экспорте или других бизнес-сущностях приложения.

#### 7. Единая система размеров и типографики

Для кнопок и текстовых элементов Toolbar на начальном этапе принять базовый размер `1rem`.

Требования:

- Размеры элементов не должны быть чрезмерно большими или слишком маленькими.
- Базовый размер текста и кнопок — `1rem`.
- Размеры и оформление должны определяться каскадом SCSS/CSS-селекторов, начинающимся от корневого HTML-элемента (host element) компонента Toolbar.
- Стили Toolbar должны быть изолированы от посторонних элементов приложения.
- Section и Section Items должны наследовать соответствующие параметры оформления через этот каскад, а не задавать произвольные размеры независимо друг от друга.

Таким образом, корневой элемент Toolbar становится точкой управления типографикой и размерами всех вложенных элементов.

### Универсальный компонент Status Bar

Реализовать отдельный универсальный переиспользуемый dummy component Status Bar в существующей библиотеке `libs/shared/ui`.

Status Bar не зависит от Toolbar и не содержит бизнес-логики. Его содержимое и оформление определяются конфигурацией, переданной извне.

#### 1. Структура Status Bar

Status Bar принимает массив секций (`Sections`).

Каждая секция содержит:

- `caption` — заголовок секции. Может быть пустым.
- `class` — имя CSS-класса для оформления секции.
- `theme` — тема оформления секции.
- `items` — массив элементов секции.

#### 2. Status Bar Section Item

Каждый элемент секции содержит:

- `text` — отображаемый текст.
- `class` — имя CSS-класса для индивидуального оформления элемента.
- `callback` — необязательная callback-функция.

#### 3. Поведение элементов

- Если для элемента передан `callback`, он вызывается при двойном щелчке (`dblclick`) по элементу.
- Если `callback` отсутствует, двойной щелчок не выполняет никаких действий.
- Не предусматриваются функции-заглушки, сообщения или стандартные действия при отсутствии callback.

#### 4. Общие требования

- Status Bar является самостоятельным компонентом и не зависит от Toolbar.
- Секции и элементы отображаются на основании переданной конфигурации.
- Тексты, CSS-классы и темы определяются вызывающей стороной.
- Компонент не содержит логики, связанной с транзакциями или другими предметными областями приложения.

### 3. Сортировка

Реализовать сортировку по трём полям:

- **Дата транзакции:** по возрастанию / по убыванию / без сортировки.
- **Тип транзакции:** по возрастанию / по убыванию / без сортировки.
- **Сумма:** по возрастанию / по убыванию / без сортировки.

Для каждого поля предусмотреть три состояния сортировки: `up`, `down`, `off`.

Сортировка выполняется только в пределах набора данных, полученного после применения фильтров. Она не должна изменять исходный набор транзакций.

### 4. Поиск

Реализовать поиск по следующим данным:

- описание транзакции;
- сумма транзакции;
- текст заметки, связанной с транзакцией.

Особенность поиска по сумме: значение суммы рассматривается как текст, а не как числовое значение.

Это позволяет выполнять поиск по части строки. Например, запрос `68` должен находить суммы `680.90` и `89.68`.

Поиск выполняется только в пределах уже отфильтрованных данных.

Поиск по другим полям не предусматривается. Если у транзакции есть заметка, её текст также участвует в поиске; найденная заметка возвращает связанную с ней транзакцию.

### 5. Последовательность обработки данных

Фильтрация определяет исходный набор транзакций, доступный для дальнейших операций.

Сортировка и поиск работают в пределах этого набора, а не по всей коллекции транзакций.

Таким образом, операции не должны обходить или отменять ограничения, заданные фильтрами.

### Цветовая система и правила использования цветов

Все цвета приложения стандартизируются в единой централизованной цветовой системе.

Единственное разрешённое место определения пользовательских цветовых токенов приложения:

`common/styles/colors/`

Структура:

```text
common/styles/
  colors/
    success.scss
    error.scss
    warning.scss
    regular.scss
    tertiary.scss
```

Обязательные правила:

- Один цветовой токен — один SCSS-файл.
- Имя файла должно соответствовать имени цветового токена.
- Все цветовые значения, варианты и миксы конкретного токена определяются исключительно в его SCSS-файле.
- Все миксы цветов каждого токена должны находиться в отдельном SCSS-файле с названием этого токена.
- Для каждого токена должны быть предусмотрены необходимые значения и миксы для Light и Dark тем.
- Запрещено определять пользовательские цветовые токены в теме Angular Material.
- Запрещено определять цвета непосредственно в стилях компонентов.
- Запрещено использовать HEX, RGB, RGBA, HSL, HSLA и именованные значения цветов непосредственно в SCSS/CSS компонентов.
- Запрещено создавать альтернативные определения цветовых токенов в других файлах.
- Все UI-компоненты используют только централизованные цветовые токены.

Angular Material 3 остаётся основой темизации компонентов, но пользовательская цветовая палитра приложения определяется исключительно в `common/styles/colors/`.

Правило распространяется на всё приложение: компоненты, страницы, таблицы, формы, диалоги, меню, состояния элементов и другие UI-элементы.

### Design Tokens и централизованная система дизайна

В статье необходимо отдельно объяснить назначение Design Tokens и причины их централизованного использования.

Design Tokens — это именованные значения, представляющие визуальные решения дизайн-системы: цвета, типографику, размеры, отступы, радиусы скругления и другие параметры интерфейса. Они позволяют описывать дизайн через семантические роли, а не через разрозненные значения, заданные непосредственно в компонентах.

В приложении источником пользовательских цветовых токенов служат SCSS-файлы в `common/styles/colors/`. Каждый токен определяется в собственном файле, где также находятся все его варианты и цветовые миксы. Эта структура является единственным разрешённым способом организации пользовательской цветовой палитры; определение таких токенов в теме Angular Material запрещено.

Компоненты должны потреблять токены, но не создавать собственные локальные варианты цветовой палитры или независимые определения визуальной системы. Такой подход обеспечивает согласованность интерфейса, упрощает поддержку Light и Dark тем и позволяет менять визуальные решения централизованно, не редактируя каждый компонент отдельно.

В статье следует показать связь между темой Material 3, SCSS и пользовательскими семантическими токенами, а также объяснить, почему Design Tokens являются частью архитектуры интерфейса, а не просто набором переменных.


### Организация и повторное использование SCSS

#### 1. Централизованные общие стили

Все страницы приложения должны использовать единый стиль базового контейнера страницы.

- Общий стиль контейнера определяется в `common/styles/page.layout.scss`.
- Общие стили приложения централизуются в `common/styles/common.scss`.
- Файл `page.layout.scss` импортируется в `common.scss`.
- Глобальные стили приложения подключаются через существующую конфигурацию Nx.
- Стиль контейнера должен обеспечивать единообразную структуру и визуальное поведение страниц приложения.

#### 2. Повторное использование стилей

При создании каждого нового стиля необходимо оценивать возможность его повторного применения.

- Если стиль потенциально может использоваться на других страницах или элементах приложения, он должен размещаться в `common/styles/`.
- Имя файла должно однозначно описывать назначение и область применения содержащихся в нём стилей.
- Общие стили не должны дублироваться в SCSS-файлах отдельных компонентов.
- Перед созданием нового стиля необходимо проверить, не существует ли уже подходящего общего решения.

#### 3. Правила именования и композиции стилей

Имена CSS-классов должны однозначно отражать назначение соответствующего элемента.

- Составные имена классов, построенные по принципу `adc__zxw`, запрещены.
- Вместо составных имён необходимо использовать комбинации независимых CSS-классов.
- Для управления визуальным представлением следует применять композицию классов и соответствующие правила CSS-селекторов.
- Стили должны оставаться простыми, понятными и удобными для сопровождения.

#### 4. Минимизация стилей компонентов

Необходимо стремиться к минимальному количеству SCSS-кода внутри отдельных компонентов.

- По возможности стили компонентов должны полностью отсутствовать.
- Предпочтение отдаётся централизованным общим стилям и повторно используемым решениям.
- Локальные стили допускаются только тогда, когда их невозможно разумно вынести в общую систему.
- Не следует создавать локальные стили исключительно ради удобства реализации отдельного компонента, если решение может быть повторно использовано.

### Типографика, размеры и расстояния

Правила являются общепроектными и распространяются на всё приложение и последующие UI-разработки.

**Типографика:**

- Основной шрифт приложения — Roboto.
- Базовый размер шрифта задаётся как 16px.
- Это единственное разрешённое использование единицы px.
- Все остальные размеры шрифта задаются исключительно в rem.

**Размеры и расстояния:**

- Все отступы и расстояния, включая margin, padding и gap, задаются исключительно в rem.
- Размеры UI-элементов — width, height, min/max размеры, размеры иконок, border-radius, border-width и позиционирование — задаются исключительно в rem.
- Использование em, %, px (кроме базового размера шрифта 16px) и любых других единиц измерения для размеров и расстояний UI-элементов запрещено.

**Ограниченное исключение для layout и интерфейсных слоёв:**

- Единицы vh и vw разрешены для задания размеров layout-контейнеров, диалоговых окон и других интерфейсных слоёв.
- vh и vw запрещено использовать для задания размеров отдельных элементов внутри этих контейнеров.
- vh и vw запрещено использовать для отступов и расстояний между элементами.

Безразмерные значения CSS, предусмотренные синтаксисом соответствующих свойств, остаются допустимыми. Например, font-weight, opacity, z-index и безразмерный line-height не требуют единиц измерения и не должны искусственно переводиться в rem.

**Обоснование выбора rem:**

Единица rem рассчитывается относительно корневого размера шрифта документа. Поэтому размеры не зависят от глубины вложенности компонентов и остаются предсказуемыми во всём приложении. Изменение базового размера позволяет согласованно масштабировать типографику и связанные с ней размеры интерфейса.

Единица em зависит от размера шрифта текущего или родительского элемента. При глубокой вложенности это может приводить к неожиданному накоплению масштаба. Проценты также зависят от контекста конкретного CSS-свойства и родительского контейнера. Отказ от этих единиц для размеров и расстояний делает систему более однозначной.

Исключение vh и vw ограничено задачами layout: размеры таких контейнеров могут определяться доступной областью просмотра. Для самих элементов внутри layout сохраняется единое правило rem.

### 6. Визуальное оформление строк таблицы

Предусмотреть различное визуальное представление приходных и расходных транзакций.

**Стандартный режим отображения:**

- **Приходные транзакции (Income):**
  - цвет текста — дизайн-токен `success`;
  - начертание — полужирное (`font-weight: 600` или соответствующий токен типографики).

- **Расходные транзакции (Expense):**
  - цвет текста — токен `regular` (чёрный);
  - стандартное начертание (`font-weight: 400`).

**Режим фильтрации «Только приход»:**

Когда пользователь выбирает отображение исключительно приходных транзакций:

- цвет `success` заменяется на `regular`;
- начертание становится стандартным;
- строки отображаются без дополнительного визуального акцента.

Цветовое и типографическое выделение используется для различения типов транзакций, когда в таблице одновременно присутствуют приход и расход.

Цвет Income использует токен `success` (тёмно-зелёный), цвет Expense — `regular` (чёрный). При активном фильтре «Только приход» цвет Income переключается с `success` на `regular`. Все остальные цвета и состояния интерфейса используют пользовательские цветовые токены из `common/styles/colors/`.

### Макет страницы Dashboard и поведение при прокрутке

Dashboard представляет собой фиксированный по размеру viewport layout. Вся доступная высота окна браузера распределяется между Page Header, Toolbar, таблицей транзакций и Status Bar.

**Общие требования к расположению:**

- ширина Dashboard — 100vw;
- высота Dashboard — 100vh;
- минимально поддерживаемый размер окна браузера — 800 × 600 px;
- общая прокрутка страницы и документа заблокирована;
- прокрутка разрешена исключительно внутри области таблицы транзакций;
- внешние отступы страницы отсутствуют;
- внутренние отступы основного контейнера страницы отсутствуют;
- высота области таблицы автоматически занимает всё пространство, оставшееся после размещения остальных элементов Dashboard.

Минимальное разрешение 800 × 600 px является требованием к поддерживаемому размеру окна. При этом действуют общепроектные правила единиц измерения: CSS-размеры и расстояния задаются в rem, а vh/vw применяются только к layout-контейнерам и интерфейсным слоям.

**Структура Dashboard сверху вниз:**

1. Page Header.
2. Toolbar таблицы транзакций.
3. Table Header.
4. Scrollable Transaction Table.
5. Status Bar.

**1. Заголовок страницы (Page Header)**

В верхней части страницы располагается заголовок с названием продукта Personal Finance.

В правой части Page Header располагаются переключатели языка и темы:

- переключатель языка;
- переключатель темы.

Переключатель языка располагается непосредственно слева от переключателя темы. Переключатель темы находится в крайней правой части заголовка, с выравниванием по правому краю страницы.

Поведение заголовка связано с прокруткой таблицы:

- при прокрутке строк таблицы вниз Page Header скрывается с анимацией roll-up;
- при прокрутке строк таблицы вверх Page Header возвращается с анимацией roll-down;
- анимация не должна запускать прокрутку всей страницы или изменять фиксированную высоту Dashboard;
- освободившееся после скрытия заголовка пространство передаётся области таблицы.

**2. Toolbar таблицы транзакций**

Toolbar располагается непосредственно под Page Header.

Требования:

- Toolbar всегда остаётся видимым;
- при скрытии Page Header Toolbar занимает верхнюю позицию Dashboard;
- содержимое Toolbar не прокручивается вместе со строками таблицы.

**Переключатель темы при скрытом заголовке:**

Когда Page Header скрывается:

- переключатель темы появляется в крайней правой части Toolbar;
- переключатель не должен дублироваться одновременно в Page Header и Toolbar.

Когда Page Header возвращается:

- переключатель темы возвращается в Page Header;
- из Toolbar он исчезает.

Таким образом, переключатель темы всегда доступен пользователю независимо от положения прокрутки таблицы.

Переключатель языка при скрытии Page Header не перемещается в Toolbar и не дублируется.

**3. Заголовок таблицы (Table Header)**

- Table Header остаётся видимым при вертикальной прокрутке строк.
- Он располагается непосредственно под Toolbar.
- При скрытии Page Header Table Header сохраняет положение под Toolbar.
- Заголовок таблицы не должен перекрываться Toolbar или областью Status Bar.

**4. Область прокрутки таблицы (Scrollable Transaction Table)**

- Прокрутка строк выполняется исключительно внутри выделенной области таблицы.
- Верхняя граница области прокрутки располагается непосредственно под Table Header.
- Нижняя граница располагается непосредственно над Status Bar.
- Область таблицы динамически занимает всё доступное пространство между Table Header и Status Bar.
- При прокрутке строки не должны уходить под Status Bar.
- Изменение видимости Page Header не должно вызывать прокрутку документа: меняется только доступная высота области таблицы.

**5. Строка состояния (Status Bar)**

В нижней части Dashboard располагается постоянно видимый Status Bar. Он не прокручивается вместе с таблицей и не перекрывается её содержимым.

Status Bar отображает:

- общее количество транзакций в текущем отображаемом наборе после применения фильтров и поиска;
- количество маркированных строк среди текущего отображаемого набора;
- общую сумму приходных транзакций в текущем отображаемом наборе;
- общую сумму расходных транзакций в текущем отображаемом наборе;
- общий баланс счёта, рассчитанный по всем транзакциям независимо от активных фильтров и поиска.

Количество и суммы прихода/расхода должны соответствовать тому набору транзакций, который в данный момент отображается в таблице. Маркировка учитывается только для строк, входящих в текущий отображаемый набор. Баланс счёта остаётся независимым от фильтрации и поиска и отражает все транзакции.

**Визуальное оформление общего баланса:**

- Размер шрифта значения общего баланса — `1.25rem`.
- Начертание — полужирное (`font-weight: 600`).
- Если значение баланса отрицательное, для его отображения используется цветовой токен `error`.
- Цвет положительного и нулевого баланса определяется стандартным цветовым токеном `regular`.

**Общее поведение Dashboard:**

- Dashboard всегда занимает ровно 100% доступной ширины и высоты окна браузера.
- Общая прокрутка страницы заблокирована.
- Page Header скрывается и появляется с анимацией roll-up/roll-down в ответ на прокрутку таблицы.
- Toolbar, Table Header и Status Bar остаются доступными.
- Прокручивается только область строк таблицы.
- Layout не допускает перекрытия элементов и сохраняет Status Bar в нижней части окна.

### 7. Маркировка строк таблицы

В левой части Toolbar добавить кнопку-иконку Checkbox для включения и выключения режима маркировки строк.

**Поведение режима маркировки:**

- При включении режима в таблице появляется дополнительная колонка слева с Checkbox для каждой строки.
- Пользователь может независимо включать и выключать маркировку каждой строки.
- Состояние маркировки хранится только в оперативном состоянии текущей сессии приложения. Оно не сохраняется в LocalStorage, IndexedDB или другом постоянном хранилище.
- После перезагрузки приложения маркировки отсутствуют.

**Выключение режима маркировки:**

- Если нет маркированных строк, повторное нажатие кнопки Toolbar штатно закрывает дополнительную колонку.
- Если есть хотя бы одна маркированная строка, повторное нажатие открывает диалог подтверждения.
- При подтверждении действия все маркировки сбрасываются, а дополнительная колонка закрывается.
- При отмене диалога режим маркировки остаётся включённым, а текущие отметки сохраняются.

**Визуальное оформление маркированных строк:**

- Фон маркированной строки оформляется цветом токена `tertiary` с интенсивностью 30% (30% opacity/alpha).
- Цвет текста не меняется и продолжает определяться существующими правилами оформления Income и Expense.
- Цвет должен поступать из централизованного токена `tertiary`; локальное определение цвета в стилях компонента запрещено.

### 8. Заметки к транзакциям

Добавить возможность создавать заметку для транзакции непосредственно из таблицы.

**Открытие и ввод заметки:**

- При двойном щелчке по строке транзакции открывается диалог добавления заметки к этой транзакции.
- Пользователь может ввести текст заметки длиной не более 1024 символов.
- В диалоге доступны действия сохранения заметки и закрытия диалога без сохранения.

**Хранение и связь с транзакцией:**

- Заметки сохраняются в IndexedDB.
- Для заметок используется отдельное хранилище/таблица; заметка не является частью записи транзакции.
- Каждая заметка имеет собственный уникальный ID.
- Связь с транзакцией устанавливается через отдельное поле ID транзакции (transactionId).
- На текущем этапе для одной транзакции допускается только одна заметка. Следовательно, transactionId должен однозначно определять заметку, а отдельный ID заметки сохраняется как самостоятельный идентификатор записи.

**Визуальная индикация заметок:**

- Строка транзакции, у которой есть заметка, получает фоновое выделение цветом токена `warning` с интенсивностью 15% (15% opacity/alpha).
- Цвет текста транзакции не меняется.
- При наведении на любую ячейку такой строки появляется Tooltip с текстом заметки.
- Цвет фона берётся из централизованного токена `warning`.

**Визуальная иллюминация транзакций:**

Если сумма расходной транзакции превышает установленный Expense transaction highlight threshold:

- строка получает красную рамку;
- фон ячеек оформляется цветом токена `error` с интенсивностью 15%;
- цвет текста не меняется.

Если сумма приходной транзакции превышает установленный Income transaction highlight threshold:

- строка получает тёмно-зелёную рамку;
- фон ячеек оформляется цветом токена `success` с интенсивностью 15%;
- цвет текста не меняется.

**Совмещение визуальных состояний:**

Если транзакция одновременно имеет заметку и превышает порог иллюминации:

- фон ячеек формируется смешиванием соответствующих цветовых токенов в пропорции 50% / 50%;
- для Expense используются `warning` и `error`;
- для Income используются `warning` и `success`;
- соответствующие цветовые миксы определяются в централизованных SCSS-файлах цветовых токенов;
- цвет текста не меняется.

### 9. Генерация тестовых данных

Подготовить миграцию тестовых данных для наполнения приложения историческими транзакциями.

Требования:

- временной диапазон: с 2021 года по текущую дату;
- количество записей: не менее 5000 транзакций;
- данные должны содержать как приходные, так и расходные операции;
- данные должны быть пригодны для проверки фильтрации по периодам, сортировки и поиска;
- генерация должна позволять воспроизводить тестовый набор данных.

Миграция должна обеспечить достаточный объём и временной охват данных для практической демонстрации возможностей таблицы.

## Ожидаемый результат

Приложение Personal Finance получает целостную основу пользовательского интерфейса на базе Angular Material 3, централизованную систему дизайн-токенов и повторно используемые компоненты там, где их применение обосновано.

Login и Dashboard поддерживают переключение между светлой, тёмной и системной темами. Выбранная настройка на Dashboard сохраняется через Facade и DAL в LocalStorage и восстанавливается при повторном открытии приложения.

Dashboard получает расширенную таблицу транзакций с единым Toolbar для управления типами операций, временными периодами (включая фильтр по году и месяцу) и наличием заметок, сортировкой по дате, типу и сумме, а также поиском по описанию, сумме и тексту заметки. Таблица поддерживает настройки порогов визуального выделения и месячных лимитов для Income и Expense, сохраняемые единым JSON-объектом в LocalStorage. Месячные алерты рассчитываются для выбранного календарного месяца. Таблица также поддерживает временную маркировку строк и заметки, сохраняемые в отдельном хранилище IndexedDB и связанные с транзакциями по ID.

Dashboard использует фиксированный layout высотой и шириной 100% viewport: прокручивается только область таблицы, Page Header скрывается и возвращается с анимацией, а Status Bar постоянно отображает количество транзакций, маркировку, суммы прихода и расхода и общий баланс.

Пользовательский период выбирается исключительно через календарные компоненты Angular Material. Ручной ввод дат невозможен.

Приходные и расходные операции визуально различаются с помощью централизованных цветовых и типографических токенов из `common/styles/colors/`. При включении фильтра «Только приход» визуальное выделение приходных строк отключается. Маркированные строки, строки с заметками и транзакции, превышающие заданные пороги, получают фоновые акценты из централизованных цветовых токенов и их миксов; текст транзакций при этом сохраняет своё стандартное цветовое оформление.

Тестовая база содержит не менее 5000 транзакций за период с 2021 года по текущую дату, что позволяет полноценно демонстрировать и проверять реализованные возможности.
