## NX Workspace Concepts and Project Organization

The previous article explained why an NX Workspace is useful and how to create an Angular application with a separate E2E project. We consider that step complete and continue with the existing workspace.

It is important to distinguish three concepts:

- **Workspace** — the working environment and its shared configuration.
- **Project** — a unit NX can discover, such as an application, library, or E2E project.
- **Target** — a named task belonging to a project, such as building, serving, or testing.

In this repository, `personal-finance` and `personal-finance-e2e` are separate NX projects with different responsibilities and available tasks. The set of targets is determined by configuration and plugins; do not assume that every project has the same `build`, `test`, and `lint` targets.

Documentation: [NX project configuration](https://nx.dev/reference/project-configuration).

### The `.angular/` and `.nx/` Support Directories

In addition to `apps/`, `libs/`, and configuration files, support directories may appear in a workspace after dependencies are installed and tools are run. They contain caches, intermediate data, or local information used by development tools, but are generally not project source code.

**`.angular/` contains Angular CLI support data.** It may include a build cache that allows results to be reused and subsequent runs to complete faster. Its contents depend on the Angular CLI version and project settings. The directory can usually be deleted: the tools will recreate the required data on the next run. Clearing the cache may make the first subsequent run slower, but should not remove application source code.

**`.nx/` contains NX support data.** Our `.gitignore` explicitly excludes these subdirectories:

- `.nx/cache` — cache of NX task results. If a task's inputs have not changed, NX can reuse a previous result instead of running the task again.
- `.nx/workspace-data` — local workspace data used by NX to operate and analyze projects.
- `.nx/migrate-runs` — data associated with NX migration runs.

These directories are excluded from Git because they contain generated or local data that is not needed to restore the source code on another machine. Their contents may differ between developers and environments, and caches can be recreated when needed. Do not confuse this support data with NX configuration files such as `nx.json`, `project.json`, and `tsconfig.base.json`: configuration defines project behavior and belongs in the repository.

The root `.gitignore` also excludes:

- `.idea/` — WebStorm/IntelliJ IDE settings and metadata, which often depend on the machine or developer preferences;
- `node_modules/` — installed dependencies restored from package manifests and the package-manager lockfile;
- `dist/` — build output that can be regenerated by running the build;
- `__screenshots__/` — locally generated screenshots that are not considered source files in this project.

The purpose of `.gitignore` is not to hide any inconvenient files; it is to keep generated artifacts and local data out of version history. Source files, settings, the lockfile, and other files required for reproducible team development must remain version-controlled.

See also: [Angular CLI cache](https://angular.dev/cli/cache) and [NX task caching](https://nx.dev/features/cache-task-results).

## Organizing `apps/` and `libs/`: common and shared

At this stage, we are not creating a collection of abstract libraries “for the future”. Instead, we establish the minimum structure that will guide the further development of Personal Finance. This requires agreement not only on where applications and libraries live, but also on the purpose of shared resources and NX project tags.

### `apps/` for Applications and `common/` for Workspace Resources

The `apps/` directory contains standalone applications and their associated test projects. Our main Angular application has the NX project name `personal-finance`. The separate E2E project, `personal-finance-e2e`, tests user scenarios in the browser. These are two different NX projects, but they belong to the same product.

The `common/` directory lives **at the workspace root**, alongside `apps/` and `libs/`. It does not belong to the application and must not be placed in `apps/personal-finance/`. It stores shared resources that are connected to the application through its configuration.

Target structure:

```text
common/
├── styles/
│   └── common.scss
└── environments/
    ├── common.ts
    ├── environment.dev.ts
    ├── environment.test.ts
    └── environment.prod.ts
apps/
├── personal-finance/
│   ├── project.json
│   └── src/
│       └── app/
└── personal-finance-e2e/
```

Shared styles live in `common/styles/common.scss` and are included separately from the application's own styles. In `apps/personal-finance/project.json`, list `apps/personal-finance/src/styles.scss` first and `common/styles/common.scss` second. This preserves the separation: the first file is responsible for application-local styles, while the second contains workspace-wide styles. The `common` directory is at the workspace root.

The main application needs three environment modes: `dev`, `test`, and `prod`. Their files are created in `common/environments/`. This requirement applies to the application, not the E2E project. The mechanism for selecting a file must be explicitly configured in the application's targets/configurations and aligned with the Angular/NX versions in use.

The `common/environments/common.ts` file exports a shared constant:

```typescript
export const COMMON = {};
```

Each environment file imports this constant and exports it through the `common` property while retaining the standard environment properties:

```typescript
import { COMMON } from './common';

export const environment = {
  production: false,
  common: COMMON,
};
```

This illustrates the configuration shape; it is not the complete content for all three files. Standard property values must match each mode. Create separate files for `dev`, `test`, and `prod` with appropriate values, and configure file selection for serving/building.

Code documentation is mandatory: **all classes and all their public or protected methods and properties must be documented in English**. Comments should explain the purpose of the class or member rather than merely repeat its name.

### Creating `common/` and Connecting Shared Resources

We will now move resources to the workspace root so that they are connected through application configuration rather than stored inside the application. Run all commands below from the repository root.

First, create the directories:

```bash
mkdir -p common/styles common/assets common/environments
```

Keep `apps/personal-finance/src/styles.scss` where it is: it contains the application's own styles. Create a separate file for workspace-wide styles:

```bash
mkdir -p common/styles
 touch common/styles/common.scss
```

If shared rules already exist, move them into `common/styles/common.scss` without moving or renaming the application's stylesheet.

There is currently one file in `apps/personal-finance/public/`: `favicon.ico`. Move it directly into `common/assets/`: the favicon is a shared workspace resource that may be used by multiple applications in the future.

```bash
mv apps/personal-finance/public/favicon.ico common/assets/favicon.ico
rmdir apps/personal-finance/public
```

In `apps/personal-finance/src/index.html`, find the existing `<link rel="icon" ...>` element and change its `href` to the path of the resource at the site root:

```html
<link rel="icon" type="image/x-icon" href="favicon.ico">
```

If the original element has additional attributes, keep them and change only `href`. Since `common/assets/` will be configured to publish files at the build output root below, `favicon.ico` will remain available at `/favicon.ico`.

The resulting shared-resource structure is:

```text
common/
├── assets/
│   └── favicon.ico         # Shared workspace favicon
├── styles/
│   └── common.scss         # Shared workspace styles
└── environments/
    ├── common.ts           # Values shared by all environments
    ├── environment.dev.ts
    ├── environment.test.ts
    └── environment.prod.ts
```

The `common/assets/` directory contains static resources connected to the application through `assets` in its `project.json`. This is not a TypeScript library: Angular copies these files into the build output, and the application can access them by URL. The shared `favicon.ico` lives at the root of `common/assets/` and is published at `/favicon.ico`; the link in `index.html` must point to that path.

#### Creating Environment Configurations

Create the shared object and three environment files. The shared object is intentionally empty for now: only settings that genuinely apply to all modes should be added here.

`common/environments/common.ts`:

```typescript
export const COMMON = {};
```

`common/environments/environment.dev.ts`:

```typescript
import { COMMON } from './common';

export const environment = {
  production: false,
  common: COMMON,
};
```

`common/environments/environment.test.ts`:

```typescript
import { COMMON } from './common';

export const environment = {
  production: false,
  common: COMMON,
};
```

`common/environments/environment.prod.ts`:

```typescript
import { COMMON } from './common';

export const environment = {
  production: true,
  common: COMMON,
};
```

These examples establish a consistent configuration shape. Settings that vary between environments can be added to `common` later, but do not put secrets here: anything included in a frontend build is accessible to the browser user.

In this approach, `environment.prod.ts` is the base file imported by the application. The `development` and `test` configurations replace it with the corresponding file through `fileReplacements`. Therefore, application code should import `environment` from `common/environments/environment.prod` rather than choosing a file manually at each usage site.

#### Updating `apps/personal-finance/project.json`

Paths to styles and static resources are relative to the workspace root. Configure `assets` and `styles` under `build.options` as follows. Application styles and shared styles are two separate entries, in this order:

```json
"assets": [
  {
    "glob": "**/*",
    "input": "common/assets",
    "output": "/"
  }
],
"styles": [
  "apps/personal-finance/src/styles.scss",
  "common/styles/common.scss"
]
```

`output: "/"` means that files from `common/assets/` are published from the site root. For example, `common/assets/images/logo.svg` will be available at `/images/logo.svg`, as if it had previously been located in `apps/personal-finance/public/images/logo.svg`.

Next, add the environments under `build.configurations`. Keep the existing `production` and `development` settings, adding `fileReplacements` to them. Also add a `test` configuration:

```json
"configurations": {
  "production": {
    "fileReplacements": [],
    "budgets": [
      {
        "type": "initial",
        "maximumWarning": "500kb",
        "maximumError": "1mb"
      },
      {
        "type": "anyComponentStyle",
        "maximumWarning": "4kb",
        "maximumError": "8kb"
      }
    ],
    "outputHashing": "all"
  },
  "development": {
    "fileReplacements": [
      {
        "replace": "common/environments/environment.prod.ts",
        "with": "common/environments/environment.dev.ts"
      }
    ],
    "optimization": false,
    "extractLicenses": false,
    "sourceMap": true
  },
  "test": {
    "fileReplacements": [
      {
        "replace": "common/environments/environment.prod.ts",
        "with": "common/environments/environment.test.ts"
      }
    ],
    "optimization": false,
    "extractLicenses": false,
    "sourceMap": true
  }
}
```

No replacement is needed in production mode: the base file is already named `environment.prod.ts`. The empty `fileReplacements` array can be omitted; it is shown only for clarity. When inserting this fragment into an existing file, do not create a second `configurations` key or remove other current project settings.

To make `nx serve personal-finance --configuration=test` use the new configuration, add this configuration to the `serve` target:

```json
"test": {
  "buildTarget": "personal-finance:build:test"
}
```

Keep the existing `development` and `production` configurations unchanged. You can then explicitly run the different variants:

```bash
npx nx build personal-finance --configuration=development
npx nx build personal-finance --configuration=test
npx nx build personal-finance --configuration=production

npx nx serve personal-finance --configuration=development
npx nx serve personal-finance --configuration=test
npx nx serve personal-finance --configuration=production
```

These are application build configurations. The `test` target that runs unit tests is a separate task and does not automatically become the `build:test` environment; configure the test runner separately as required by the selected executor.

Verify the resulting configuration and builds:

```bash
npx nx show project personal-finance
npx nx build personal-finance --configuration=development
npx nx build personal-finance --configuration=test
npx nx build personal-finance --configuration=production
```

After moving the resources, check the application in the browser as well as checking the build. From the workspace root, run:

### `libs/shared/`: Shared Libraries with Explicit Responsibilities

The `libs/` directory contains separate NX libraries. At this stage, we will use `libs/shared` for libraries intended to be used by multiple parts of the application and expected to preserve framework-independent boundaries wherever possible.

The initial set contains four libraries:

```text
libs/
└── shared/
    ├── facades/
    ├── dal/
    ├── base/
    └── definitions/
        ├── abstracts/   # Abstract TypeScript classes
        └── classes/     # Regular classes
```

These are four independent NX projects, not merely four folders of code. Each project must have its own configuration and explicitly defined tags. Creating the libraries establishes expected responsibility boundaries; it does not mean we must immediately fill each one with many classes. First, create the required structure and minimal entry points, then add implementation as requirements emerge.

#### Generating Libraries with NX Commands

Create the four libraries from the workspace root. In this project, use the `@nx/js:lib` generator: it is suitable for shared TypeScript libraries that do not need Angular components or other framework-specific elements. The command `npx nx g` is shorthand for `npx nx generate`.

During generation, NX may ask which bundler to use to build the library. At this stage, choose **`none`**: we do not need a separate build configuration for each internal library while establishing the architectural skeleton and configuring dependencies. This is a deliberate simplification, not a claim that a bundler will never be needed. If we later need to publish a library as a standalone package or build it independently, revisit the choice based on distribution format and project requirements.

**A bundler and a test runner are different tools.** Choosing `none` for library builds does not mean abandoning tests. We plan to use **Vitest** for unit tests, provided the selected Nx version and generator support the required configuration. If the generator asks separately about the test runner, choose Vitest; if it does not, configure testing in a separate step and verify the generated targets and configuration files. Do not assume Vitest is configured automatically just because the library was generated successfully.

Run the commands one at a time and inspect the generated `project.json` after each generation:

```bash
npx nx g @nx/js:lib libs/shared/facades --tags="level:shared,tag:facades"
npx nx g @nx/js:lib libs/shared/dal --tags="level:shared,tag:dal"
npx nx g @nx/js:lib libs/shared/base --tags="level:shared,tag:base"
npx nx g @nx/js:lib libs/shared/definitions --tags="level:shared,tag:definitions"
```

If the generator version in use asks for additional parameters, choose settings consistent with the current workspace and verify the result against the rules below. These commands illustrate the intended structure; they do not replace checking the generated files.

Each project must have:
- an expected NX project name matching the library name;
- the tags `level:shared` and `tag:<project-name>`;
- a public entry point, `src/index.ts`, for `facades`, `dal`, and `base`;
- an alias in the root `tsconfig.base.json` that follows the repository conventions.

For `definitions`, use category-specific public entry points only: `libs/shared/definitions/src/lib/<category>/index.ts`. This architecture **must not** have a shared `libs/shared/definitions/src/index.ts`. This allows individual categories to be imported through separate aliases without creating one barrel for all definitions.

Create seven categories and their `index.ts` files from the repository root:

```bash
#!/usr/bin/env bash
set -euo pipefail

base="libs/shared/definitions/src/lib"
categories=(constants abstracts classes enums types interfaces records)

for category in "${categories[@]}"; do
  mkdir -p "${base}/${category}"
  cat > "${base}/${category}/index.ts" <<EOF
/**
 * Public exports for shared ${category}.
 * Add explicit exports when files are introduced.
 */
export {};
EOF
done
```

The script creates category entry points only. When real files are added to a category, replace `export {}` with explicit exports of existing files, for example `export * from './account.type';`. Do not use `export * from './';`: it points back to the same directory and can create a circular reference.

The `@nx/js:lib` generator may also create starter files named `definitions.ts` and `definitions.spec.ts`. They are not needed in this architecture: instead of one starter module, we use categories with separate `index.ts` files. Delete both generated files completely. If the generator placed them in the standard `src/lib/` directory, run this from the workspace root:

```bash
rm -f libs/shared/definitions/src/lib/definitions.ts
rm -f libs/shared/definitions/src/lib/definitions.spec.ts
```

If your generator version created these files elsewhere, remove the generated `definitions.ts` and `definitions.spec.ts` inside `libs/shared/definitions/` at their actual locations. Do not remove the category files `src/lib/<category>/index.ts`: they are the public entry points.

Verify that seven category entry points exist and that the library has no common entry point:

```bash
find libs/shared/definitions/src/lib -maxdepth 2 -type f -name 'index.ts' -print
test ! -f libs/shared/definitions/src/index.ts
```

On Windows, use Git Bash or WSL to run this Bash script. The category aliases in `tsconfig.base.json` must point to `libs/shared/definitions/src/lib/<category>/index.ts`:

- `@workshop:def:consts` → `libs/shared/definitions/src/lib/constants/index.ts`
- `@workshop:def:abstracts` → `libs/shared/definitions/src/lib/abstracts/index.ts`
- `@workshop:def:classes` → `libs/shared/definitions/src/lib/classes/index.ts`
- `@workshop:def:enums` → `libs/shared/definitions/src/lib/enums/index.ts`
- `@workshop:def:types` → `libs/shared/definitions/src/lib/types/index.ts`
- `@workshop:def:interfaces` → `libs/shared/definitions/src/lib/interfaces/index.ts`
- `@workshop:def:records` → `libs/shared/definitions/src/lib/records/index.ts`

After generation, inspect the discovered projects and graph:

```bash
npx nx show projects
npx nx graph
```

The generator may update configuration and add files, but it does not know every architectural convention in this repository. Check the names and tags in every `project.json`, ensure aliases point to existing files, and only then proceed with implementation. Import boundaries are configured separately in the root ESLint configuration through `@nx/enforce-module-boundaries`.

**`facades` — application services and API facades.** This library contains services through which the application interacts with APIs and uses application operations. A facade may coordinate calls and provide a convenient consumer contract, but it must not contain UI logic specific to a particular frontend framework. For example, an Angular component, its template, UI state, or presentation code must not be placed in the shared facade library merely because several screens use it.

**`dal` — Data Access Layer.** This library handles access to data from different sources: backend APIs and other external or internal sources. It centralizes low-level data retrieval and persistence mechanisms, source-response transformations, and related technical contracts. Data access should be separated from the UI, and transport logic should not be duplicated in components. The exact dependency direction between `facades` and `dal` must be established separately when designing the contracts, to avoid cycles.

**`base` — shared foundational functionality.** This library contains fundamental capabilities needed throughout the application that do not belong to one specific feature. Shared helpers for text internationalization are one example. Do not move arbitrary code here merely because it is “shared”; the library's responsibility must remain small and explainable.

**`definitions` — shared definitions and contracts.** This includes constants, types, enums, records, interfaces, facade contract types, and functions independent of the UI and frameworks. The `abstracts/` directory is for abstract TypeScript classes, while `classes/` is for regular classes. The library should provide definitions and base classes needed by multiple projects, rather than becoming a place for implementing every service. Contract definitions may be used by both facades and data-access layers, so this library must remain foundational and must not depend on higher-level libraries.

The word “shared” is not, by itself, a sufficient reason to extract code into a library. When choosing a library, understand which responsibility it centralizes, who consumes it, and which dependencies are allowed. If a function belongs to a specific screen or feature, do not move it to `libs/shared` merely for the sake of reuse.

### Mandatory NX Project Tags

For the NX graph and future architectural boundary rules to rely on conventions, every project must have tags in its `project.json`. A directory on disk does not assign tags by itself: verify the actual configuration when creating each project.

**Every application project and its associated E2E project** must have the common tag `level:app` and an individual tag `app:<project-name>`, where the name comes from the `name` field in that same `project.json`. For example, the `personal-finance` application should have:

```json
{
  "name": "personal-finance",
  "projectType": "application",
  "tags": ["level:app", "app:personal-finance"]
}
```

For the separate E2E project named `personal-finance-e2e`, the tags are `["level:app", "app:personal-finance-e2e"]`. The shared `level:app` tag allows app-level rules to apply to both the application and E2E project, while `app:<project-name>` distinguishes them.

**Every library inside `libs/shared`** must have two tags:

- `level:shared` — indicates that the project belongs to the shared level;
- `tag:<library-name>` — an individual tag whose name matches the `name` field in `project.json`.

For example, the `facades` library project should contain:

```json
{
  "name": "facades",
  "projectType": "library",
  "tags": ["level:shared", "tag:facades"]
}
```

The same principle applies to `dal`, `base`, and `definitions): each library keeps the `level:shared` tag and adds its own individual tag, respectively `tag:dal`, `tag:base`, or `tag:definitions`. Additional tags may be present if they follow explicitly agreed architectural rules.

Tags only classify projects by themselves. They do not automatically prohibit undesirable dependencies. Permitted import directions and their rationale are defined in the next section; for the restrictions to take effect, configure them in ESLint using NX's `@nx/enforce-module-boundaries` rule.

Thus, `common/` at the workspace root stores shared workspace-level resources, while `libs/shared/*` contains independent libraries with defined responsibilities and tags. This separation allows the structure to evolve without mixing application resources, UI logic, and shared technical contracts.

## NX Module Boundaries: Dependency Rules

Tags describe the role of each NX project, while **module boundaries** restrict dependency directions between projects. The goal is not to make imports harder, but to preserve architectural boundaries: the application should not bypass facades and access the data layer directly, and foundational libraries must not depend on application-level libraries.

We use the following rules in this workspace:

| Source project | Allowed dependency tags | Rationale |
| --- | --- | --- |
| `level:app` | `tag:facades`, `tag:definitions`, `tag:base` | The application uses application facades, shared contracts, and foundational capabilities, but does not access the DAL directly. |
| `tag:facades` | `tag:dal`, `tag:base`, `tag:definitions` | Facades coordinate application operations, use data access, and rely on shared contracts and foundational functionality. |
| `tag:definitions` | `tag:base` only | Definitions remain a low-level layer. They must not know about facades or data access. |
| `tag:dal` | `tag:base`, `tag:definitions` | The data layer can use shared contracts and utilities, but must not depend on application orchestration. |
| `tag:base` | No workspace projects | `base` is fully isolated: it imports no other workspace projects, existing or future. |

Why this matters:

- **The application depends on facades, not on data-storage implementation.** Otherwise, components and the application begin to know API and data-source details, and changing an implementation affects too much code.
- **Facades coordinate interaction scenarios.** They can call the DAL and combine operations, hiding data-source details from consumers.
- **Definitions must not pull in application layers.** Otherwise, shared types and contracts cease to be a stable foundation, circular dependencies may appear, and reuse becomes harder.
- **The DAL depends on contracts and foundational tools, but not on facades.** This keeps the technical data-access layer unaware of who calls its methods or why.
- **Base remains a completely isolated foundation.** `base` must not import any other workspace project—not `definitions`, `dal`, `facades`, applications, or any future project. This is intentionally strict: the foundation must not pull in external contracts, domain details, or application mechanisms. If functionality requires a dependency on another project, place it in another layer instead of weakening this restriction.

The restrictions are configured in the root `eslint.config.mts` using NX's `@nx/enforce-module-boundaries` rule and the `depConstraints` array: each `sourceTag` has an allowed `onlyDependOnLibsWithTags` list. Invalid dependencies should produce lint errors. After adding or renaming a project, check its tags and run lint to verify that the NX graph and rules classify it as expected.

### A Consistent ESLint Configuration Extension: `.mts`

In this workspace, we will use the `.mts` extension for all three ESLint flat configuration files: the root configuration and the application and E2E configurations. The `.mts` extension denotes a TypeScript module in ES Modules format and is consistent with configurations such as `vitest.config.mts`. This is a file-format convention; renaming the file alone does not change lint rules.

In ESLint 9, loading a TypeScript `.mts` configuration in standard Node.js mode requires the `jiti` package. Install it as a dev dependency:

```bash
npm install --save-dev jiti
```

Rename all three files so references and conventions remain consistent:

```bash
git mv eslint.config.mjs eslint.config.mts
git mv apps/personal-finance/eslint.config.mjs apps/personal-finance/eslint.config.mts
git mv apps/personal-finance-e2e/eslint.config.mjs apps/personal-finance-e2e/eslint.config.mts
```

Update the import of the root configuration in both project configurations. In `apps/personal-finance/eslint.config.mts` and `apps/personal-finance-e2e/eslint.config.mts`, it must point to `../../eslint.config.mts`:

```typescript
import baseConfig from "../../eslint.config.mts";
```

Leave the other rules and imports unchanged. After renaming, verify that the configurations load and the lint targets work:

```bash
npx nx lint personal-finance
npx nx lint personal-finance-e2e
```

Run the second command if the E2E project has a `lint` target configured. If ESLint reports that a configuration cannot be found or loaded, check the filenames, relative import paths, presence of `jiti` in `package.json` and the lockfile. If the decision is to use `.mts` throughout the workspace, do not leave some configuration files with the `.mjs` extension.

The `app:<project-name>` tag identifies a specific app-related project; it does not replace the common `level:app` tag. The E2E project gets `level:app` for workspace-level classification, but its test configuration remains separate from the application's runtime environment settings.

Documentation: [Enforce module boundaries](https://nx.dev/features/enforce-module-boundaries).

## Creating Shared Libraries and TypeScript Path Aliases

When creating each library in `libs/shared/`, configure not only its NX project and required tags but also register a public alias in the root `tsconfig.base.json`. This lets consumers import the library's public API using a stable name instead of long relative paths.

Use separate aliases in the form `@workshop:<library-name>` for `facades`, `dal`, and `base`; each points to the library's own `src/index.ts`. For `definitions`, do not use a shared `src/index.ts): each category has its own `index.ts` under `libs/shared/definitions/src/lib/<category>/`, and imports use a separate alias `@workshop:def:<category>`. If the library generator created `libs/shared/definitions/src/index.ts`, delete that file: the public API of `definitions` is organized through separate category entry points, so a common barrel is unnecessary. Do not delete the `index.ts` files inside category directories.

```json
{
  "compilerOptions": {
    "paths": {
      "@workshop:facades": ["./libs/shared/facades/src/index.ts"],
      "@workshop:dal": ["./libs/shared/dal/src/index.ts"],
      "@workshop:base": ["./libs/shared/base/src/index.ts"],
      "@workshop:def:consts": ["./libs/shared/definitions/src/lib/constants/index.ts"],
      "@workshop:def:abstracts": ["./libs/shared/definitions/src/lib/abstracts/index.ts"],
      "@workshop:def:classes": ["./libs/shared/definitions/src/lib/classes/index.ts"],
      "@workshop:def:enums": ["./libs/shared/definitions/src/lib/enums/index.ts"],
      "@workshop:def:types": ["./libs/shared/definitions/src/lib/types/index.ts"],
      "@workshop:def:interfaces": ["./libs/shared/definitions/src/lib/interfaces/index.ts"],
      "@workshop:def:records": ["./libs/shared/definitions/src/lib/records/index.ts"],
      "base": ["./libs/shared/base/src/index.ts"],
      "dal": ["./libs/shared/dal/src/index.ts"],
      "facades": ["./libs/shared/facades/src/index.ts"]
    }
  }
}
```

Each category alias must point to the public entry point `src/lib/<category>/index.ts`. The `definitions` library has no common `src/index.ts`: consumer code uses the specific `@workshop:def:<category>` aliases. When adding a category, create its directory and `index.ts`, add an alias to `tsconfig.base.json`, and export only the API intended for consumers.

While categories are empty, keep a temporary compilable stub in each category `index.ts`. Do not use `export * from './';`: that points to the same directory and can create a circular reference.

For `libs/shared/definitions/src/lib/types/index.ts`:

```typescript
/**
 * Public exports for shared type definitions.
 * Add exports here when types are introduced.
 */
export {};
```

Use the same pattern for the other categories, adjusting the comment to reflect the category's purpose:
- `constants/index.ts` — shared constants;
- `abstracts/index.ts` — shared abstract classes;
- `classes/index.ts` — shared classes;
- `enums/index.ts` — shared enums;
- `types/index.ts` — shared type definitions;
- `interfaces/index.ts` — shared interfaces;
- `records/index.ts` — shared records.

When real files are added to a category, replace the temporary stub with explicit exports of existing files, for example `export * from './account.type';`.

**Important:** the `definitions` library must not contain a common `libs/shared/definitions/src/index.ts` file. Delete it if the NX generator created one. This rule applies only to the library's root entry point; category `index.ts` files inside `src/lib/<category>/` are required and must remain.

Since this workspace does not define `baseUrl`, all values in `paths` start with `./`; otherwise TypeScript may report `TS5090`.

Example imports:

```typescript
import { SomeType } from '@workshop:def:types';
import { SomeConstant } from '@workshop:def:consts';
```

Do not import another library's internal files through relative paths: consumers should use its public API. Path aliases provide convenient and stable paths, but **do not replace** module boundaries and do not, by themselves, prohibit forbidden dependencies.

## Project Configuration and Targets

NX must know which projects belong to the workspace and which operations are available for them. This information is defined by project configuration and the installed tooling. Depending on the plugins in use, some targets may be explicitly defined in configuration files while others may be discovered automatically from project settings.

A **target** is a named task that can be run for a project. For example, a project may provide targets for building, serving, testing, or checking code style. Do not assume that every project has the same set of targets: it depends on the project's purpose and configuration.

You can inspect the resolved configuration of a particular project with NX:

```bash
npx nx show project personal-finance
```

This command shows how NX sees the `personal-finance` project, including its available targets. This is more useful than drawing conclusions from filenames or assuming that every project should have `build`, `test`, and `lint` commands.

Do not confuse the workspace-wide configuration with individual project configuration. The `nx.json` file defines settings that apply to the workspace and NX behavior in general. Project configuration describes a specific project and its tasks; it may be stored in `project.json` or produced through the configuration-discovery mechanisms used by plugins.

As a result, configuration becomes an interface between the project and development tools. Developers and CI can use it to understand which actions are available, and NX can use it to coordinate their execution.

Documentation: [NX workspace configuration](https://nx.dev/reference/nx-json) and [NX project configuration](https://nx.dev/reference/project-configuration).

## How NX Discovers Projects and Runs Tasks

As the repository grows, it is useful to find out which projects NX actually discovers instead of maintaining a manual list. Run:

```bash
npx nx show projects
```

The command lists the projects NX recognizes in the current workspace. It is a useful starting point when exploring a repository or after changing configuration. The directory structure helps explain how the code is organized, but the NX project list shows which units it can actually work with.

Once you know a project name, inspect its configuration separately:

```bash
npx nx show project personal-finance
```

Tasks are run by specifying the project name and target. The general form is:

```bash
npx nx run personal-finance:build
```

Here, `personal-finance` is the project name and `build` is the target. The command works only if that target exists and is configured for the project. Therefore, inspect the available configuration first and then run the required task.

This approach scales with the repository: you do not need to remember every detail of a specific bundler or test tool when a project exposes the corresponding task through NX. NX does not replace the tools themselves; it coordinates their execution based on configuration and installed plugins.

## Serving, Building, Testing, and Linting

Everyday development uses different checks because each answers a different question:

- **Serving the application** lets you inspect it during development.
- **Building** checks whether the project can be built with the current configuration.
- **Unit tests** check individual pieces of behavior.
- **Linting** detects issues related to static-analysis rules and code style.
- **E2E tests** check user scenarios through the application and its environment.

NX provides a common way to run these actions through project targets. For example, if the project has the corresponding targets, commands may look like this:

```bash
npx nx run personal-finance:build
npx nx run personal-finance:test
npx nx run personal-finance:lint
```

These examples show the syntax; they do not claim that every project necessarily has all three targets. Determine the available commands from the actual project configuration. E2E checks use a separate project, so first find its exact name and available targets with `npx nx show projects` and `npx nx show project <project-name>`.

### Adding Convenient npm Scripts to `package.json`

NX commands can be run directly with `npx nx`, but it is often convenient to give frequently used operations short names in the root `package.json`. This provides a single entry point for developers and CI: the invocation details live in the repository rather than in personal notes.

Add a `scripts` object to the root `package.json`, or extend the existing one without removing other scripts:

```json
{
  "scripts": {
    "serve": "nx serve personal-finance",
    "build": "nx build personal-finance",
    "build:all": "nx run-many -t build",
    "build:prod": "nx build personal-finance --configuration=production",
    "test": "nx run-many -t test",
    "lint": "nx run-many -t lint",
    "nx:graph": "nx graph",
    "affected": "nx affected -t lint test build"
  }
}
```

What the commands do:

- `npm run serve` — serves the main Personal Finance application in development mode.
- `npm run build` — builds the `personal-finance` application.
- `npm run build:all` — runs the `build` target for projects that have it configured; it does not assume every project has a build.
- `npm run build:prod` — builds the application with the production configuration.
- `npm test` — runs `test` targets for projects where they are available.
- `npm run lint` — runs lint for projects that have the corresponding target configured.
- `npm run nx:graph` — opens the project graph visualization.
- `npm run affected` — runs lint, tests, and builds for projects NX considers affected by changes.

The `build:all`, `test`, and `lint` scripts use `nx run-many` because their purpose is to run the same task across multiple projects. The `build` script is intentionally limited to the main application. To check only one project, keep using targeted commands such as `npx nx lint personal-finance`.

The `affected` command depends on the Git comparison range. For local runs, ensure the base revision is available and appropriate for the task; in CI, the target branch's base revision and the current revision are usually specified explicitly. For example:

```bash
npx nx affected -t lint test build --base=origin/main --head=HEAD
```

Replace `origin/main` if your workflow uses a different target branch. You can add a separate npm script with a fixed base branch, but avoid hard-coding one if local and CI workflows use different bases.

After adding the scripts, verify that their names match the actual project targets. If a target is missing, NX cannot run that task for the project; first inspect the configuration with `npx nx show project <project-name>`.

The point of this section is not to repeat the command list from the previous article. The important thing is to understand the NX model: a command addresses a specific project and target, and NX runs the corresponding task while accounting for configuration and dependencies.

This provides a consistent interface for local development and automation. However, a shared command does not guarantee test quality, correct linting, or comprehensive checks. Their purpose and quality still depend on configuration and the team's engineering decisions.

## The Project Graph and the Task Graph

As a workspace grows, it becomes increasingly important to understand not only which projects exist but also how they are connected. NX builds a **project graph**, representing discovered dependencies between projects. Inspect it with:

```bash
npx nx graph
```

The graph helps explore the workspace and answer practical questions: which projects use this library? Which parts of the system may be affected by a change to shared code? Has one library become a dependency of too much of the application?

The graph itself does not tell us whether the architecture is good. It shows discovered dependencies, but cannot automatically decide whether a particular relationship makes sense in terms of business responsibility. That requires architectural agreements and analysis of why the projects interact.

The **task graph** answers a different question: which operations must run, and in what order? One task, for example, may depend on another finishing first. NX can take project relationships and configured task dependencies into account when planning execution.

Thus, the project graph describes relationships between projects, while the task graph describes relationships between operations to be performed. The graphs are related, but they are not interchangeable.

The distinction becomes especially important in large repositories. A change to a shared library may affect several applications, while running a task for one application may require prerequisite operations. Graphs make these relationships explicit instead of relying solely on individual developers' knowledge.

See: [Explore the project graph](https://nx.dev/features/explore-graph).

## Caching and Affected Commands

As a workspace grows, rerunning every check after each change can take increasingly long. NX supports **task caching**: when a task is configured for caching and its inputs match a previously computed result, NX can reuse that result instead of executing the task again.

Caching does not mean that every command automatically becomes faster. To produce a correct result, NX must account for the data that influences the task: source files, configuration, dependencies, and other configured inputs. If a task depends on external state or performs side effects, its suitability for caching must be evaluated separately. An incomplete description of inputs can make result reuse incorrect.

Another capability is to run tasks only for projects affected by changes. **Affected** commands identify the relevant set of projects based on changes and the dependency graph. This is especially useful in CI, where running every check across the entire repository can be expensive.

The general command form is:

```bash
npx nx affected -t lint test build --base=<base-revision> --head=<current-revision>
```

The values `<base-revision>` and `<current-revision>` are placeholders that must be replaced with real Git revisions appropriate for the scenario. In CI, these are often the target branch's base revision and the revision being checked. Do not blindly copy the same pair into every workflow: the base depends on what you want to compare.

Affected commands do not replace an understanding of dependencies either. Their effectiveness depends on correct project discovery, the graph, and task configuration. Before claiming that CI time has been reduced, configure the scenario for the repository and measure the result.

Caching and affected solve different problems: caching reuses a task result when inputs match; affected identifies which tasks should be considered for the changed part of the workspace. Together they can reduce unnecessary work, but do not remove the need to configure and verify the process properly.

Documentation: [Task caching](https://nx.dev/features/cache-task-results) and [Affected commands](https://nx.dev/ci/features/affected).

## Early Architectural Decisions Without Premature Abstraction

NX provides mechanisms for organizing a workspace, but it does not choose the architecture for the team. Directory structure and the dependency graph show how code is technically organized; they do not prove that responsibilities are divided correctly.

Before creating a library, identify the stable responsibility it will isolate and the problem a separate boundary will solve. Sometimes a structure within the application is sufficient; sometimes a library helps control dependencies, reuse code, or define a public contract. The decision should depend on how the code changes and who uses it, not on a desire to create familiar `domain`, `data-access`, `ui`, or `shared` folders in advance.

A practical principle is: identify the problem first, choose the boundary next, and only then enforce it with NX rules. Tags and `@nx/enforce-module-boundaries` are useful when they protect a deliberate architectural decision; by themselves, they do not replace that decision.

Documentation: [Enforce module boundaries](https://nx.dev/features/enforce-module-boundaries).

## Scope of This Stage: Preparing the Skeleton

At this stage, I usually finish preparing the project's skeleton: the workspace, core shared libraries, naming conventions, path aliases, and strict dependency boundaries. This provides a predictable foundation for further development, but it is not yet an implementation of the business domain.

Structural separation into layers and explicit dependency rules already overlap to some extent with architectural ideas found in Domain-Driven Design. However, we are not designing a domain model, bounded contexts, aggregates, or domain events here. **DDD will be covered separately in the next dedicated article**, so that preparing the technical skeleton is not mixed with domain modeling.
