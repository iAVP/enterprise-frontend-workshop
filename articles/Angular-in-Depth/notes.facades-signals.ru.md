# Angular in Depth — заметки: Facades, Signals и управление состоянием

> Статус: рабочие авторские заметки. Это материал для продолжения статьи и практической реализации Personal Finance, а не готовый текст для публикации.

## Глава 3. Facades, Signals и управление состоянием

### Архитектурная цель

Продолжить развитие Personal Finance и заменить первоначальную, упрощённую реализацию более последовательной архитектурой. Компоненты должны оставаться максимально простыми и декларативными. Управление состоянием, координация операций и frontend-логика должны находиться за пределами компонентов.

### 1. Авторизация и начальная маршрутизация

- При открытии приложения состояние авторизации проверяется через API соответствующего фасада.
- Неавторизованный пользователь должен попадать на Login, а не на Dashboard.
- После успешного входа пользователь может перейти на Dashboard.
- Компоненты и маршруты не должны самостоятельно реализовывать проверку авторизации в обход фасада.

### 2. Facade как API для компонентов

- Бизнес-состояние приложения принадлежит соответствующим Facade Services.
- Компоненты получают состояние через read-only Signals.
- Изменять состояние можно только через публичные методы фасада.
- Фасад координирует операции, выполняет frontend-логику и проверки до изменения или сохранения данных.
- Компоненты отвечают преимущественно за отображение, пользовательский ввод и передачу действий фасаду.
- Локальные Signals внутри компонента допустимы, если они действительно нужны для временного состояния конкретного UI-элемента или сложной формы. Такое решение должно иметь ясное обоснование.
- Не следует без причины смешивать Signals с обычными properties компонента и создавать неоднозначное поведение Change Detection.

### 3. Реактивное обновление Dashboard

- Формы доходов и расходов должны изменять состояние через фасад.
- После сохранения и возврата на Dashboard он должен отображать актуальные данные без ручного обновления страницы.
- Производные значения, например суммы доходов, расходов и общий баланс, должны вычисляться централизованно, а не дублироваться в компонентах.
- Пока функциональные домены приложения отдельно не разделяются. При этом границы ответственности фасадов и DAL следует проектировать так, чтобы последующее разделение не потребовало переписывать весь поток данных.

### 4. Computed и Effect

- Основной механизм для производных значений — computed на уровне фасада; компонент только читает результат.
- Необходимо отдельно объяснить, как computed отслеживает зависимости и чем он отличается от effect.
- Автор отмечает практический опыт, когда computed не обновлял ожидаемые значения во всех проверявшихся сценариях, тогда как effect позволял явно обновлять внутренние Signals. Это наблюдение нужно проверить на актуальной версии Angular и не превращать в универсальное утверждение о поведении computed.
- Effect не следует добавлять автоматически. Его применение должно быть связано с конкретным побочным действием или архитектурным сценарием.
- В текущем варианте приложения формы доходов и расходов открываются как отдельные страницы. Пользователь сохраняет данные и возвращается на Dashboard; для этого сценария отдельный effect пока не требуется.

### 5. Storage и DAL

- Компоненты не должны обращаться напрямую к localStorage, sessionStorage или IndexedDB.
- Для компонентов единая точка входа — Storage Facade. На данном этапе не нужно преждевременно разделять его на отдельные Local Storage, Session Storage и IndexedDB фасады.
- Storage Facade выбирает подходящее хранилище и предоставляет понятный API остальному приложению.
- Низкоуровневая работа с IndexedDB, включая открытие базы, транзакции и механизмы чтения/записи, должна находиться в DAL.
- DAL не должен вызываться непосредственно из UI-компонентов.
- При повторной инициализации приложения состояние восстанавливается из постоянного хранилища через фасад и DAL. При навигации между страницами фасад может продолжать хранить актуальное состояние в памяти.

### 6. Краткая историческая подводка

Перед техническим разбором Signals дать краткий обзор эволюции подходов к управлению состоянием и реактивности:

- от ручного управления событиями и подписками к более декларативным реактивным моделям;
- роль RxJS и то, что для эффективного применения RxJS разработчику нужно освоить его модель потоков, Observable, операторы и управление подписками;
- Signals как более непосредственная модель реактивного состояния, упрощающая многие повседневные сценарии;
- уменьшение количества ручной инфраструктуры вокруг подписок и жизненного цикла компонентов.

Историческую часть не превращать в утверждение, что Signals заменяют RxJS. У каждого подхода своя область применения; RxJS остаётся важным инструментом для потоков и сложных асинхронных сценариев.

## Глава 4. Modal Dialogs и Effect — план следующего этапа

Следующий этап должен логически продолжить главу о фасадах и Signals и показать сценарий, в котором Effect действительно имеет практический смысл.

### План реализации

1. Сначала завершить вариант с отдельными страницами доходов и расходов: фасады, Signals, computed, авторизация и доступ к хранилищу через Storage Facade и DAL. В этой версии не вводить Effect без необходимости.
2. На следующем этапе преобразовать формы добавления доходов и расходов из отдельных страниц в модальные диалоги.
3. Сохранить управление состоянием и операции сохранения за фасадами. Модальный UI не должен получать прямой доступ к DAL или браузерным хранилищам.
4. На сценарии модального диалога показать, где и зачем нужен Effect: например, для координации побочного действия, связанного с открытием/закрытием диалога или реакцией на изменение состояния. Конкретное применение выбрать после анализа реализации, а не вводить искусственный эффект ради демонстрации API.
5. Показать полный поток: Dashboard открывает диалог, пользователь вводит данные, фасад выполняет проверки и сохранение, состояние обновляется, диалог закрывается, Dashboard отображает актуальные значения.
6. Отдельно объяснить, почему в предыдущем варианте с навигацией между самостоятельными страницами Effect не требовался, а в новом сценарии модального взаимодействия может появиться обоснованная задача для него.

### Разделение реализации на Git-ветки

- `Angular-in-Depth+1` — базовый вариант: Facades, Signals, computed, авторизация и Storage Facade/DAL; формы остаются отдельными страницами, без Effect.
- `Angular-in-Depth+2` — следующий вариант: формы доходов и расходов становятся модальными диалогами; добавляется обоснованный пример использования Effect.

Вторая ветка должна продолжать первую, чтобы разница между двумя этапами была видна в истории реализации.

## Редакционные оговорки

- Канонический технический текст статьи ведётся на английском языке; этот файл — русскоязычные авторские заметки для фиксации решений.
- Не выдавать предварительные архитектурные решения за окончательные до проверки реализации.
- Не использовать Effect только потому, что он входит в Signals API.
- Не смешивать вычисление производного состояния, загрузку данных из хранилища и побочные действия: это разные задачи.
- Не утверждать, что computed «не отслеживает все изменения» без воспроизводимого примера и проверки актуальной версии Angular.
